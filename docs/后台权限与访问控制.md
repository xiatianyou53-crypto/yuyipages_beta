# 后台权限与访问控制

> 面向管理员。回答三个问题：**谁能在后台改内容**、**怎么限制只有指定的人能改**、**怎么对外开放投稿**。

---

## 一、现状快照（写档时实测）

| 项目 | 现状 |
|---|---|
| 仓库可见性 | **public（公开）** |
| `/admin/` 门禁 | **无 Cloudflare Access**（任何人可打开登录页） |
| 后台后端 | Decap CMS `github` 后端 + 自建 OAuth Worker（负责换 token） |
| 发布方式 | 直接提交到 `main`（**没有**草稿/审核流程） |

---

## 二、谁能改内容？

**取决于"是否为该仓库的协作者（Write 权限）"，而不是"是否有 GitHub 账号"。**

| 身份 | 能打开后台 | 能看到文章 | 能保存/修改 |
|---|---|---|---|
| 协作者（角色 = Write） | ✅ | ✅ | ✅ |
| 有 GitHub 账号，但**不是**协作者 | ✅（能完成授权） | ✅（仓库 public，内容本就公开） | ❌ **保存会被 GitHub 拒绝**（403 / permission denied） |
| 未登录的访客 | — | ✅（可直接浏览仓库） | ❌ |

> 常见困惑：非协作者登录后能**看到完整内容**、也能在编辑器里**看起来**改字，但一按保存就报权限错误——因为最终提交是用**他自己的 token** 调 GitHub API。
> 我们的 OAuth Worker **不校验**代理者是否为协作者（它只负责换取 token），权限边界由 GitHub 仓库权限决定。

## 三、三种控制方式

### A. 只加协作者（现状机制，零成本）
GitHub → 仓库 → **Settings → Collaborators and teams → Add people** → 角色给 **Write**。
- 移出编辑者：同一页面 Remove 即可，**立即生效**（对方 token 随即无法提交）。
- 适合：编辑人员固定、就几个人。

### B. 给 `/admin` 加 Cloudflare Access（推荐，把入口也关上）

最短步骤：
1. 打开 `https://one.dash.cloudflare.com` → **Zero Trust → Access → Applications → Add an application → Self-hosted**
2. **Application domain**：`yuyipages-beta.pages.dev`（或你的自定义域名），**Path 填 `/admin`**
3. **Policy**：名称如 `编辑部`，Action = **Allow**，规则用 **Emails**（或 Email domain / 一次性验证码），把允许的邮箱逐个填进去
4. 保存。此后访问 `/admin/` 会**先**要求邮箱验证码登录，**再**进入 Decap 的 GitHub 登录（两道门）
5. 可再补一条 `Action = Block` 的兜底策略，或只保留 Allow

> Zero Trust 免费版支持最多 50 名用户，本项目规模足够。
> 好处：外人**连后台页面都打不开**，不会出现"登录了却报错"的困惑。

### C. 允许"任何人都能投稿"（Fork + PR 流程）

仓库已是 public，具备启用条件。在 `static/admin/config.yml` 的 `backend` 下增加：

```yaml
backend:
  name: github
  repo: MTeaCase/yuyipages_beta
  branch: main
  base_url: https://yuyi-cms-oauth.xiatianyou53.workers.dev   # 你的 Worker 域名
  auth_endpoint: auth
  open_authoring: true          # ← 新增
```

影响与注意：
- 非协作者编辑时会走 **Fork → 自动创建 Pull Request**，由维护者在 GitHub 审核并合并；
- **合并前内容不会上线**（相当于天然的审核流程）；
- 需要提前告知投稿者"你的改动会以 PR 形式提交"；
- 编辑体验会变慢（要先 fork），且 PR 会堆在仓库里需要有人处理。

## 四、常见疑问

**Q：非协作者能进后台看到内容，是不是漏了？**
正常。因为仓库是 public，Decap 读取内容走 GitHub API，任何登录者都能读。**能读 ≠ 能改**。

**Q：保存时报 403 / not permitted？**
该 GitHub 账号没有该仓库的 Write 权限。把他加成协作者即可。

**Q：能把仓库改回 private 吗？**
可以（Settings → General → Danger Zone → Change visibility）。改回 private 后：
- 非协作者**连内容都读不到**（登录后会看不到列表）；
- 已公开过的历史与内容**无法撤回**；
- Cloudflare Pages 的仓库集成一般照常工作，若报错重新连接一次仓库即可。

**Q：前台网站会因此受限吗？**
不会。网站是构建好的静态产物，**访客不需要任何权限**；权限只影响"谁能编辑/提交"。

**Q：改 GitHub 用户名会影响权限吗？**
不影响。协作者、SSH key、OAuth 授权都跟着**账号**走；只是仓库里写死仓库名的位置（如 `config.yml` 的 `repo`）需要同步更新。

## 五、建议组合

| 定位 | 推荐做法 |
|---|---|
| 只有编辑部能改 | **A + B**（协作者白名单 + Access 白名单），最省心 |
| 欢迎全校投稿 | **C**（open_authoring），并配一个维护者负责合并 PR |
| 想尽量不公开 | 仓库改回 **private**，并保留 **B** 作为入口门禁 |
